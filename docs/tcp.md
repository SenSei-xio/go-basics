## 一、三次握手

### 1. 状态流转表（必背，面试白板第一张图）

| 步 | 谁发 | 发什么 | 客户端状态 | 服务器状态 |
|---|---|---|---|---|
| 开始时 | — | — | `CLOSED` | `LISTEN` |
| ① | 客户端 → 服务器 | `SYN`（我的初始序号 x） | **`SYN_SENT`** | `LISTEN` |
| ② | 服务器 → 客户端 | `SYN + ACK`（我的序号 y，确认你的 x） | `SYN_SENT` | **`SYN_RCVD`** |
| ③ | 客户端 → 服务器 | `ACK`（确认你的 y） | **`ESTABLISHED`** | **`ESTABLISHED`** |

**一句话**：客户端**发完**第③步就进 `ESTABLISHED`，服务器**收到**第③步才进——**客户端早半个瞬间**。

### 2. 实跑证据：握手花多少时间

输出（`6_握手时间线.go`）：

```
[客户端] 调用 Dial 前        : 15:26:44.901523
[客户端] Dial 返回（已连上） : 15:26:44.923245 err = <nil>
[服务器] Accept 返回         : 15:26:44.923771
```

**本地回环 21.7 毫秒**。`Dial` 是阻塞的，它返回时**握手已经完成**，可以立刻读写。

### 3. netstat 三种状态现场

**① 还没人连：**
```
TCP    0.0.0.0:19001          0.0.0.0:0              LISTENING
```

**② 握手第 1 步发出去了，对方没回（连 10.255.255.1:9999）：**
```
TCP    192.168.1.176:61073    10.255.255.1:9999      SYN_SENT
```
> **`SYN_SENT` = 「我喊了，没人应」，不是「我没喊」。** 能出现在 netstat 里就说明包已经发出去了。

**③ 握手完成，双方 ESTABLISHED（同一个连接两个视角）：**
```
TCP    127.0.0.1:19001        127.0.0.1:57190        ESTABLISHED
TCP    127.0.0.1:57190        127.0.0.1:19001        ESTABLISHED
```

### 4. 为什么三次不是两次、不是四次

- **两次不够**：① 服务器确认不了客户端能不能收；② **防不住延迟的旧 SYN**——很久以前的 SYN 包在连接关掉后到达，服务器以为新连接、回 SYN+ACK 建好，然后**干等一个不会有人用的连接**，这就是**半开连接**。
- **四次多余**：第②步的 SYN 和 ACK 是 TCP 头里两个独立标志位，本来就能同时置 1，合并省一次往返。

**一句话记法：两次防不住旧包，四次只是把②拆两半。**

## 二、四次挥手

### 1. 状态流转表（必背）

| 步 | 谁发 | 发什么 | 主动关方状态 | 被动关方状态 |
|---|---|---|---|---|
| 开始时 | — | — | `ESTABLISHED` | `ESTABLISHED` |
| ① | 主动方 → 被动方 | `FIN`（我没数据要发了） | **`FIN_WAIT_1`** | `ESTABLISHED` |
| ② | 被动方 → 主动方 | `ACK`（知道了） | **`FIN_WAIT_2`** | **`CLOSE_WAIT`** |
| ③ | 被动方 → 主动方 | `FIN`（我也没数据要发了） | `FIN_WAIT_2` | **`LAST_ACK`** |
| ④ | 主动方 → 被动方 | `ACK`（知道了，再见） | **`TIME_WAIT`**（等 2MSL） | `CLOSED` |

**两条状态链（手打记住）：**

```
主动关方：ESTABLISHED -> FIN_WAIT_1 -> FIN_WAIT_2 -> TIME_WAIT -> CLOSED
被动关方：ESTABLISHED -> CLOSE_WAIT -> LAST_ACK -> CLOSED
```

### 2. 实跑证据（netstat 抓到的真实现场）

**服务器故意不 Close，一直是 CLOSE_WAIT：**
```
TCP    127.0.0.1:19003        127.0.0.1:57097        CLOSE_WAIT     <- 被动关方
TCP    127.0.0.1:57097        127.0.0.1:19003        FIN_WAIT_2     <- 主动关方
```

**服务器也 Close 之后，只剩主动方的 TIME_WAIT：**
```
TCP    127.0.0.1:49680        127.0.0.1:19020        TIME_WAIT
```

> **一句话：TIME_WAIT 永远属于「先动手的那一方」。谁先 Close，谁等 2MSL。**

### 3. 为什么挥手四次、握手三次

**握手时双方手里都空着**（还没传数据），状态对称 -> SYN 和 ACK 能合并成一步。
**挥手时一方可能还有数据没发完** —— A 说「我不发了」（FIN），B 只能先回 ACK（「收到你的话头了」），等自己数据发完才能发 FIN -> **② 和 ③ 不能合并**。

**一句话：握手时都空着手，所以能合并；挥手时一方手里可能还有货。**

## 三、TIME_WAIT / CLOSE_WAIT（面试最常追问）

### 1. 区别表（必背）

| | `TIME_WAIT` | `CLOSE_WAIT` |
|---|---|---|
| 谁在 | **主动关方** | **被动关方** |
| 正常吗 | **正常**，是设计的一部分 | **不正常**，是 bug |
| 原因 | 等 2MSL | 对方发了 FIN，**你还没 Close()** |
| 后果 | 占本地端口 | **占文件描述符，泄漏** |
| 线上症状 | 端口不够用 | `too many open files`，拒绝新连接 |

### 2. TIME_WAIT 为什么要等（两个理由，缺一不可）

**理由一：怕最后那个 ACK 丢了**
```
主动方：ACK -> （丢了）
被动方：没收到 ACK，重发 FIN
主动方：还在 TIME_WAIT 就认得它 -> 再回 ACK  OK
        如果已经关了 -> 当陌生包 -> 回 RST   对方报错
```

**理由二：让旧包过期**
同一四元组立刻复用时，网络里残留的旧包可能被当成新连接的包。等 2MSL 保证全死光。

### 3. TIME_WAIT 堆积的真实后果（实跑验证）

**客户端用固定本地端口连 40 次（5 个端口轮着用）：**
```
成功 5 失败 35
connectex: Only one usage of each socket address (protocol/network address/port) is normally permitted.
```
**-> TIME_WAIT 会挡住客户端复用本地端口。**

**服务端监听端口堆了 12 条 TIME_WAIT，新连接还能进吗：**
```
=== TIME_WAIT 条数 ===
12
=== 客户端结果 ===
TIME_WAIT 堆积后，新连接结果: err = <nil>
```
**-> 服务端完全不受影响。** 因为服务端本地端口固定（如 19008），变的是对端端口；四元组各不相同，不会耗尽监听端口。

> **常见错误答案**：「TIME_WAIT 占满服务端端口导致连不上新连接」——**错**。服务端端口不会被占满；真连不上是 `too many open files`（文件描述符耗尽）或 accept 队列满。

### 4. 三个解法

1. **让客户端主动关**（服务端别 Close，等客户端先关）—— 最根本
2. `SO_REUSEADDR`（Go 的 `net.Listen` **默认就开着**）—— 解决的是「重启时端口被占」，**不减少 TIME_WAIT**
3. 服务端用 **keep-alive 长连接** —— 减少连接总数，TIME_WAIT 相应减少

## 四、面试六问六答（背这一段就够）

**Q1：三次握手过程中客户端和服务器分别处于什么状态？**
> 客户端 `CLOSED -> SYN_SENT -> ESTABLISHED`；服务器 `LISTEN -> SYN_RCVD -> ESTABLISHED`。客户端发完第③步就进 ESTABLISHED，服务器收到第③步才进。

**Q2：为什么握手三次，挥手四次？**
> 握手时双方手里都空着，SYN 和 ACK 能合并；挥手时 A 说「我不发了」，但 B 可能还有数据没发完，ACK 和 FIN 不能合并。**握手两次不够**，因为防不住延迟的旧 SYN（会造成半开连接）。

**Q3：TIME_WAIT 有什么用？**
> 两个：① 防止最后那个 ACK 丢失导致对方收不到确认；② 让这个四元组上的旧包全部过期，不被新连接误收。等 2MSL。

**Q4：线上看到大量 CLOSE_WAIT 说明什么？**
> 说明被动关闭那一方的代码收到 FIN 后没有 `Close()`，是 bug，会泄漏文件描述符。查 `defer conn.Close()` 有没有写、有没有提前 return 跳过、panic 后有没有 recover。

**Q5：TIME_WAIT 太多怎么办？**
> 首先要分清在谁身上：在客户端是本地端口不够，解法是改用长连接或复用一个 Client；在服务端不影响监听端口，真连不上是 fd 耗尽。根治办法是**让客户端主动关**。

**Q6：netstat 看 SYN_SENT 说明什么？**
> SYN 已经发出去了，在等 SYN+ACK。可能原因：对方没开、防火墙拦截、IP 写错、路由不可达。**不是「没发出去」。**
