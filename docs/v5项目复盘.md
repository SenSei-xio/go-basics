## 一、一句话说清这个项目

**一个 HTTP 服务，接收下载任务，后台用一个 goroutine 从任务表里捞活，带超时和取消，能查状态、能取消、能限流。**

面试开场可以这么说（背下来）：

> "我写了一个小型的下载服务。客户端 POST 一个 URL 过来，服务端把它存进一个带锁的 map，返回一个任务 ID。后台有一个常驻 goroutine 轮询这个 map，发现了排队中的任务就取出来真的去下载，全程带 3 秒超时，超时或者被取消就停下来。另外提供两个接口：一个查状态，一个取消。整个服务加了日志中间件和并发限流。"

## 二、架构（面试官一定会问「你的项目怎么分层的」）

### 2.1 两个执行体

```
┌─────────────────────────────────────────┐
│  main goroutine                          │
│  http.ListenAndServe(":8080", nil)       │
│    ↓ 每个请求 Go 自动起一个 goroutine     │
│  /download  /cancel  /status             │
└──────────────┬──────────────────────────┘
               │  唯一联系：任务表（map + Mutex）
               ↓
┌─────────────────────────────────────────┐
│  后台工人 goroutine                       │
│  for { 找「已排队」→ 标「下载中」→ 下载 } │
└─────────────────────────────────────────┘
```

**关键一句**：HTTP 服务是「接口」，后台工人是「干活的手」，它们**不是直接调用关系**，通过共享的 `任务表` 通信，所以**必须加锁**。

### 2.2 四个接口

| 方法 | 路径 | 参数从哪来 | 干什么 |
|---|---|---|---|
| POST | `/download` | body JSON `{"url":"..."}` | 建任务，返回 ID |
| GET | `/status?id=1` | **URL 查询串** | 查状态 |
| POST | `/cancel` | body JSON `{"id":1}` | 取消任务 |

**必背**：`GET 用 URL 带参数，POST 用 body 带参数。`（第 3 块考点，我答错过）

### 2.3 任务状态机

```
已排队 ──→ 下载中 ──→ 已完成
   │          │
   │          ├──→ 失败（HTTP 404）
   │          ├──→ 失败（超时）
   │          └──→ 已取消（用户取消，丢弃结果）
   └──→ 已取消（还没开始就被取消）
```

## 三、四个真实踩过的坑（面试话术 · 最重要的一部分）

> 这四个都是**我写完第一版之后自己发现的缺陷**，不是从教程抄的。
> 面试讲法统一是四段：**现象 → 怎么发现的 → 怎么改 → 为什么这么改**。

### 坑 1：`/cancel` 没有日志

**现象**：三个接口里，`/download` 和 `/status` 都套了 `日志(...)` 中间件，只有 `/cancel` 没套。

**怎么发现的**：做完之后回头看 `main` 里的三行路由注册，发现 `http.HandleFunc("/cancel", 取消任务)` 少了 `日志` 包装——同一类东西三个里有一个不一样，**不一致就是 bug**。

**怎么改**：
```go
http.HandleFunc("/cancel", 日志(取消任务))
```

**面试怎么讲**：
> "我的日志中间件是统一包装 Handler 的，但我第一版漏了一个接口。`/cancel` 恰恰是三个接口里最该记日志的——它是唯一一个会改变已有任务状态的接口。我后来总结了一个习惯：看到同类东西有三个、其中一个写法不一样，先假设它是 bug，不要替它找理由。"

**这条的加分点**：面试官问「你怎么保证质量」时，这就是例子——**靠一致性检查，不是靠测试覆盖**。

---

### 坑 2：没有限流，可以被瞬间打爆

**现象**：`/download` 只要请求合法就无条件 `make` 一个任务塞进 map。如果客户端一秒钟发一万个请求，任务表会无限膨胀，内存直接爆。

**怎么发现的**：想「这个接口能被什么方式滥用」时想到的。**一个不需要登录、不需要任何成本的写接口，必须假设它会被人狂打。**

**怎么改**：用**带缓冲的 channel 当令牌桶**。
```go
任务名额 = make(chan struct{}, 100)   // 最多 100 个在途任务

// 收任务里，Method 检查之后、Decode 之前：
select {
case 任务名额 <- struct{}{}:        // 有名额，占一个
    // 继续
default:                            // 名额满了
    返回错误(w, http.StatusTooManyRequests, "任务队列已满，请稍后再试")
    return
}

// 任务处理完（成功/失败/超时/取消）都要释放：
<-任务名额
```

**实测**：把上限临时改成 2 之后，第 3、4 个请求立刻返回 `{"error":"任务队列已满，请稍后再试"}`，**被拒的请求只花 1.0062 毫秒**——说明拒绝得很快，没有拖慢服务。

**面试怎么讲**：
> "我用带缓冲的 channel 做令牌桶。channel 的容量就是并发上限，`select` 加 `default` 是非阻塞的检查——有名额就占一个，没有立刻走 default 返回 429。这种方式不用引入任何第三方库，几行代码就够。**关键点是 `default` 不能省**，不写 default 的话 `select` 会一直阻塞，整个 HTTP 请求就卡死了。"

**延伸问「为什么不用现成的限流库」**：这项目就一个接口要限，标准库够用，引入依赖反而增加维护成本。

### 坑 3：错误返回格式不统一

**现象**：第一版所有错误都用 `http.Error(w, 消息, 状态码)`，它返回的是**纯文本**。但成功返回的是 **JSON**。客户端拿到错误时得先判断 Content-Type 才知道怎么解析——**同一个接口两种格式，客户端没法写统一的错误处理**。

**怎么发现的**：用 curl 逐个测错误分支时，看到成功是 `{"id":1,...}`、失败是 `只接受 POST` 一行纯文本，对比太明显。

**怎么改**：写一个统一的错误函数，9 处 `http.Error` 全换掉。
```go
func 返回错误(w http.ResponseWriter, 状态码 int, 消息 string) {
    w.Header().Set("Content-Type", "application/json")
    w.WriteHeader(状态码)
    fmt.Fprintf(w, `{"error":%q}`+"\n", 消息)
}
```
**注意参数顺序反过来了**：`http.Error` 是 `(w, 消息, 状态码)`，我的是 `(w, 状态码, 消息)`——因为状态码在前更好读，但**改的时候全部要跟着换**。

**实测四种错误全部变成 JSON**：
```
GET /download     → 405  {"error":"只接受 POST"}
缺 id             → 400  {"error":"缺少 id 参数"}
id=abc            → 400  {"error":"id 必须是数字"}
id=99             → 404  {"error":"没有这个任务"}
```

**面试怎么讲**：
> "我的原则是**同一个接口，成功和失败的响应格式必须一样**。第一版成功返回 JSON、失败返回纯文本，客户端要写两套解析。我后来加了一个统一错误函数，所有错误都走它，保证 Content-Type 和结构一致。这也是 REST API 的一个基本约定——错误体也应该是有结构的，最好带 error code。"

**延伸问「为什么用 `%q`」**：`%q` 会自动给字符串加引号并转义，避免消息里有双引号时把 JSON 弄坏。

### 坑 4：取消的任务会被覆盖成「已完成」（**最值钱的一个**）

**现象**：用户点了取消，状态变成「已取消」。但后台工人**已经开始下载了**，下载完它还会写一次状态——把「已取消」**覆盖成「已完成」**。用户明明取消了，刷新一看变成成功了。

**怎么发现的**：这个最隐蔽。是走查状态流转时想到的——「取消」只改了 map 里的状态字段，**没有检查工人手里那个任务**。

**怎么改**：工人下载完之后、写状态之前，**再检查一次状态**。
```go
任务表锁.Lock()
if 要做的.Status == "已取消" {
    任务表锁.Unlock()
    子取消()          // 把这次 HTTP 请求的 ctx 取消掉
    <-任务名额         // 释放名额
    fmt.Println("任务被取消，丢弃结果", 要做的.URL)
    continue          // 直接放弃，不写「已完成」
}
任务表锁.Unlock()
```

**实测**（用故意慢 2 秒的服务器，下载到 0.4 秒时取消）：
```
[日志] POST /download 耗时 0s
开始下载 http://127.0.0.1:18083/a.txt
[日志] POST /cancel 耗时 0s
任务被取消，丢弃结果 http://127.0.0.1:18083/a.txt
最终状态 = 已取消     ← 正确保留，没有被覆盖
```

**面试怎么讲**：
> "这是并发系统里典型的**竞态**：两个执行体都在写同一个字段，谁后写谁赢。用户取消是主 goroutine 写的，工人完成是后台 goroutine 写的，工人后写就把取消覆盖了。
> 我一开始以为加个 Mutex 就够了，但**Mutex 只保证不写坏数据，不保证业务逻辑正确**——两个操作各自都加锁了，顺序还是可能反。
> 解决办法是在**提交前再检查一次前置条件**，也就是常说的 CAS 思想：先检查状态没变，再写结果。检查完到写之间持锁，保证原子性。"

**这条为什么值钱**：它是「会写代码」和「懂并发」的分界线。面试官问「你遇到过什么并发问题」时，讲这个比讲「数据竞争」高级得多——**数据竞争是编译期能查出来的，这个是编译期查不出来的业务竞态。**

## 四、三个设计决策（面试必问「你为什么这么设计」）

### 决策 1：为什么用 `map[int]*任务` 而不是 `[]任务`

**实测数据**：10 万个任务，查 10 万次
- 切片：**1.98 秒**
- map：**1.45 毫秒**
- **慢 1370 倍**

**两个层面的答案**（都要说）：
1. **`map` 解决「找得快」**：切片按 ID 查要遍历 O(n)，map 是 O(1)
2. **`*任务` 解决「改得到」**：`map[int]任务` 取出的是**副本**，改副本原件不变；`map[int]*任务` 取出的是**指针**，直接改到原件

**面试话术**：
> "我用了 `map[int]*任务`。map 是因为三个接口都要按 ID 查任务，切片要 O(n) 遍历，实测 10 万任务下慢 1300 多倍。指针是因为 Go 的 map 取出来是值的副本，存值的话改了副本原件不变，还得再写回去——存指针就没这个问题，这也是为什么 `/cancel` 能直接改到状态。"

### 决策 2：为什么用轮询，不用 channel 通知

**这是面试官最爱的追问点。**

**我为什么没用 channel**：第一直觉是「有任务了就往 channel 里塞，工人从 channel 里取」，更优雅。但想清楚后发现三个问题：

1. **任务表还得留**：`/status` 和 `/cancel` 都要按 ID 查任务，所以 map 必须留着 → **channel 里的任务和 map 里的任务是两份数据 = 两份真相**，会不一致。用户取消的是 map 里那个，channel 里那个照样会被下载。
2. **谁发通知？** 如果在 HTTP handler 里发，通道满了会**阻塞 HTTP 请求**；如果另起一个 goroutine 发，那还是轮询。绕一圈又回来了。
3. **取消了收不回**：channel 里的任务已经被工人拿走了，取消没法撤回。

**结论一句话**：
> **有「状态表」的系统用轮询，只有「消息流」的系统才用 channel。** 我的系统需要按 ID 查状态、需要取消，所以必须有一张表，那就老老实实轮询。

**面试官可能反驳「轮询浪费 CPU」**：
> "我加了 200 毫秒的 `time.Sleep`，没活干的时候 CPU 占用是 0。如果真的追求极致，可以做**混合方案**：轮询 + 一个通知 channel，有任务时先塞 channel 唤醒工人，channel 里没东西再回退到轮询。但那是优化，不是第一版该做的事。"

### 决策 3：为什么超时是 3 秒

**三条约束**：
1. **必须大于正常下载耗时**——不然正常的任务会被误杀
2. **必须小于用户能忍的时间**——不然用户干等
3. **业界常见区间 3~10 秒**

**实测**（服务器每次响应 1 秒）：

| 超时设置 | 结果 |
|---|---|
| 300ms | **超时**，实际只等了 300ms——正常任务被误杀 |
| 3s | 成功，1.001s |
| 30s | 成功，1.001s |

300ms 那行就是「超时设太短」的现场：本来就该 1 秒完成的任务，被 300ms 的阈值砍掉了。

**面试话术**：
> "3 秒是个折中值。设太短会误杀正常的长任务，设太长用户会干等。更专业的做法是分层设置：连接超时 3 秒、读响应头超时 5 秒、整体超时 30 秒。我这个项目是单机小服务，一个总超时就够了。"

## 五、几个细节考点（面试可能突然问）

### 5.1 `select + default` 为什么必须写 default

不写 default 的话，如果 channel 满了，`select` 会**一直阻塞**等待有空位——整个 HTTP 请求就卡死了。

### 5.2 为什么 `defer 任务表锁.Unlock()` 比手动 Unlock 好

手动 Unlock 有三个坑：
1. 中间有 `return` 就漏了
2. panic 时漏了
3. 改代码时新加了 return 忘了加 Unlock

`defer` 免疫这三个。**记法：Lock 的下一行就写 `defer Unlock()`。**

### 5.3 为什么锁外面还要干活

**实测**：持锁 3 秒的话，`/status` 要等 **2.9 秒**才返回；不持锁 **0 秒**。

**一句话**：**锁只包读写共享数据的那几行，耗时操作一律放在锁外。超过 1 毫秒的操作都不该待在锁里。**

### 5.4 为什么 `err` 和 `StatusCode` 都要判

- `err` 看「通不通」：DNS 失败、连不上、超时
- `StatusCode` 看「成不成」：404、403、500

**实测**：请求一个 404 的地址 → `err = <nil>`、`resp.StatusCode = 404`。**只看 err 会把 404 页面当成下载成功。**

### 5.5 为什么读走 body 很重要

**实测**：20 次请求不读 body → **建了 20 条 TCP 连接**；`io.Copy(io.Discard, resp.Body)` → **1 条**。

**原理**：body 不读完，连接就没法复用，每次都要新建。`io.Discard` 是个「黑洞」，写进去的东西全扔，但**字节数照样算**，比 `io.ReadAll` 省内存。

### 5.6 ctx 为什么不需要加锁

**一句话**：**读的不用锁，写的要锁。**

ctx 是不可变的，`cancel()` 的实现是 `close(通道)` 而不是「改内容」。close 是并发安全的，而且 close 之后所有 `<-ch` 立刻返回。所以 100 个 goroutine 同时 `<-ctx.Done()` 一点问题都没有，`-race` 零警告。

### 5.7 为什么 `go 后台工人` 必须写在 `ListenAndServe` 前面

`ListenAndServe` 是**阻塞**的，写在它后面的代码**永远不会执行**。

**实测**（我第二次犯这个错）：把 `go 后台工人(根ctx)` 写在 `ListenAndServe` 后面 → 编译通过、不报错、POST 也正常返回「已排队」，但查状态**永远「已排队」**，日志里 `开始下载` 出现 **0 次**。

**这是最坑的一类 bug**：不崩溃、不报错、静默失败。

### 5.8 优雅关闭没做（已知缺陷，要主动承认）

`ListenAndServe` 正常阻塞时，`defer 根取消()` **永远不执行**；按 Ctrl+C 时 **defer 一行都不跑**（进程被直接杀掉）。

**正确做法**：监听 SIGINT/SIGTERM，然后调 `srv.Shutdown(ctx)`。

**面试话术**：
> "这个项目我没做优雅关闭，Ctrl+C 时后台正在下的任务会被硬杀。正确做法是监听信号，调 `Server.Shutdown` 让它在途请求处理完。这是我知道但没做的，因为当前版本是单机演示，程序退出时任务本来就没了。"

**主动说出没做的部分，比被问出来强。**

## 七、这个项目能写进简历吗

**能，但只能这么写**（不许夸大）：

> **并发下载服务**（Go，个人项目）
> - 实现 HTTP 服务接收下载任务，后台 goroutine 轮询任务表异步执行，支持任务查询与取消
> - 用 `map[int]*任务` + `sync.Mutex` 管理共享状态，`context` 实现单任务 3 秒超时与级联取消

> - 修复了一个并发竞态：已取消的任务会被后台工人覆盖为「已完成」，通过在提交前二次校验状态解决

## 八、30 秒电梯陈述（背这段）

> "这是我自己写的一个 Go 下载服务，244 行单文件。客户端 POST 一个 URL，服务端建任务存在带锁的 map 里返回 ID，后台一个常驻 goroutine 轮询任务表，捞到排队的任务就真的去下载，带 3 秒超时。另外有查状态和取消两个接口。
>
> 做完第一版之后我自己找出了四个缺陷并修掉了：一个接口漏了日志、没有限流能被瞬间打爆、错误返回格式不统一、还有一个并发竞态——取消了的任务会被工人覆盖成已完成。
>
> 最后这个我觉得是最有意义的，因为它让我明白：**加锁只能保证数据不写坏，保证不了业务逻辑正确**，还得在提交前做二次校验。"
